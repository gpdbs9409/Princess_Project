# 사이드프로젝트 기록 3. 서버비가 5달러일 줄 알았는데 20달러가 된 과정

지난 글에서 AI 비용을 줄인 이야기를 썼는데요. 이번엔 반대로 **돈을 더 쓰기로 한 이야기**입니다.

30일 챌린지 서비스를 만들고 있고, 백엔드는 Railway에 올려두었습니다. Railway는 Hobby
요금제가 월 $5라서 저는 당연히 $5만 나갈 줄 알았어요.

## 5달러가 아니라 8달러

청구서를 보니 $8이었습니다.

물론 3달러 차이는 큰 돈이 아닙니다. 그런데 저는 그것보다 **왜 초과됐는지를 모르는 게**
더 신경쓰였어요. 참가자가 아직 본격적으로 들어오지도 않았는데 벌써 초과라면, 사람이
늘면 어떻게 되는 건지 감이 안 잡히잖아요.

Railway는 $5에 사용량 크레딧 $5가 포함되어 있고, 그걸 넘으면 초과분이 청구되는 구조입니다.
그래서 대시보드에서 어디에 쓰였는지를 봤습니다.

> **[이미지] Railway 사용량 대시보드 캡처 — 항목별 비용 비중**

## 범인은 DB 용량이 아니었다

저는 막연히 **데이터가 쌓여서** 돈이 나가는 줄 알았습니다. DB 용량이라던가, 인증 사진
저장이라던가요.

그런데 아니었어요.

**대부분이 CPU와 메모리 비용이었습니다.**

생각해보면 당연한 거였습니다. Railway는 vCPU-시간과 메모리 GB-시간으로 과금합니다.
저장 용량은 거기서 아주 작은 부분이고요. 즉 **"얼마나 저장했냐"가 아니라 "얼마나 오래
켜져 있었냐 × 얼마나 많은 메모리를 쥐고 있었냐"**가 돈입니다.

그리고 저희 백엔드는 Spring Boot입니다. JVM이 올라가 있으면 요청이 하나도 안 와도
메모리를 계속 쥐고 있어요. 참가자가 0명이어도 24시간 돈이 나가고 있었던 겁니다.

인증 사진 3,600장 저장하는 것보다, **아무도 안 쓰는 새벽 시간에 서버가 켜져 있는 게**
더 비쌌던 거죠.

## JVM 힙을 건드리는 게 무서웠다

원인을 알았으니 해결책도 나옵니다. JVM이 잡는 힙 크기를 제한하면 됩니다.
`-XX:MaxRAMPercentage` 같은 옵션으로요.

그런데 여기서 손이 멈췄습니다.

힙을 너무 조이면 어떻게 되냐면.. 평소엔 멀쩡히 돌다가 **트래픽이 몰리는 순간
OutOfMemoryError로 죽습니다.** 그리고 그게 하필 참가자들이 인증 사진 올리는 시간대에
터지면요?

이 서비스는 예치금 10만원이 걸려 있습니다. 인증을 못 올려서 그 주 환급을 못 받으면
그건 그냥 버그가 아니라 **돈 문제**가 됩니다.

그러니까 문제는 이거였어요. **운영 서버에서 실험을 할 수가 없다.**

## 그래서 dev 환경을 만들었습니다

너무 당연한 결론인데, 저는 여기까지 와서야 만들었습니다. 그전까지는 로컬에서 돌려보고
바로 운영에 올리고 있었어요. 혼자 만드는 사이드프로젝트니까 그래도 된다고 생각했거든요.

실제로 사고도 있었습니다. DB에 컬럼을 하나 추가하는 변경을 했는데, 마이그레이션 SQL을
안 돌린 채로 배포해서 서버가 아예 안 뜬 적이 있어요. 스키마 검증에 걸려서요.
dev 환경이 있었으면 거기서 먼저 걸렸을 겁니다.

Railway는 한 프로젝트 안에 Environment를 여러 개 둘 수 있습니다. 그래서 `prod`와
`dev` 두 개를 같은 템플릿으로 만들었어요. 서버·MySQL·버킷이 각각 따로 생기니까
**DB가 완전히 분리**됩니다. 테스트 데이터가 운영에 섞일 일이 없고요.

브랜치도 나눴습니다.

```
dev 브랜치      → Railway dev 환경
develop 브랜치  → Railway prod 환경 + Vercel
```

그런데 환경이 두 개가 되니 당연히 돈도 두 배가 됩니다. **최소 $15 정도**가 되더라고요.

## 여기서 이메일 인증이 껴들었다

비슷한 시기에 비밀번호 찾기 기능을 붙이고 있었습니다. 참가자가 비밀번호를 까먹으면
운영진이 DB에서 직접 바꿔주고 있었는데, 그게 계속 갈 수는 없으니까요.

메일을 보내야 하는데, 여기서 막혔습니다.

> **[이 부분에 이메일 인증 시행착오 내용 채우기]**
> - 어떤 방식을 먼저 시도했는지
> - 어떤 에러/증상이 났는지 (SMTP 포트 관련)
> - 외부 메일 서비스(Resend 등)를 검토했다가 접은 이유 — 발신 도메인을 따로 사야 했음
> - 결국 Railway에서 SMTP를 열려면 요금제를 올려야 한다는 걸 알게 된 과정

결론만 쓰면, **아웃바운드 SMTP를 쓰려면 요금제를 올려야 했습니다.**

## 그래서 20달러

Pro가 월 $20입니다. 이미 dev+prod로 $18 정도를 쓰고 있었으니, **실제로 늘어난 건
$2였어요.** 이렇게 쓰고 보니 별 일 아닌 것 같은데, 결정하기까지는 위의 과정을 다 거쳤습니다.

정리하면 이렇습니다.

| 단계 | 월 비용 | 이유 |
| --- | --- | --- |
| 처음 예상 | $5 | Hobby 요금제 |
| 실제 청구 | $8 | CPU·메모리 초과분 |
| dev 환경 추가 | $15~18 | 운영에서 실험할 수 없어서 |
| Pro 전환 | $20 | 이메일 발송(SMTP) |

## 덤으로 얻은 것: DB 백업

Pro로 오면서 알게 된 건데, 볼륨 백업을 스케줄로 걸 수 있더라고요. 일간/주간/월간으로요.

사실 저는 그때까지 **백업을 아예 안 하고 있었습니다.** 더 부끄러운 건, dev 환경을
만들면서 "이제 DB가 두 개니까 백업도 되는 거 아닌가?" 하고 잠깐 생각했다는 거예요.

전혀 아닙니다. dev DB는 prod와 완전히 다른 데이터를 들고 있는 별개 인스턴스입니다.
**환경 분리는 백업이 아니에요.** prod가 날아가면 dev는 아무 도움이 안 됩니다.

인증 기록이 곧 환급 근거인 서비스에서 백업이 없었다는 건 좀 아찔한 일이었습니다.
지금은 일간 스케줄을 걸어뒀고, 정산 시점에는 로컬로도 한 벌 받아두려고 합니다.

## 여기서 남은 것

이번에 배운 걸 두 가지로 정리하면요.

**첫째, 서버 비용은 "얼마나 저장하냐"가 아니라 "얼마나 켜져 있냐"로 나갑니다.**
저는 데이터가 쌓이는 걸 걱정했는데, 실제로는 아무도 안 쓰는 시간에 JVM이 메모리를
쥐고 있는 게 더 비쌌습니다. 감으로 짐작하지 말고 대시보드를 봐야 하는 이유입니다.

**둘째, 요금제를 올린 건 성능이 아니라 안전장치를 사기 위해서였습니다.**
$20 중에 서버가 빨라져서 낸 돈은 없습니다. 전부 "운영에서 실험하지 않기 위해",
"메일을 보내기 위해", "데이터를 잃지 않기 위해" 낸 돈이에요.

지난 글에서는 AI 비용을 24,000원 줄였고, 이번 글에서는 서버비를 늘렸습니다. 반대인 것
같지만 저는 같은 얘기라고 생각합니다. **줄일 수 있는 건 줄이고, 사야 하는 건 사는 것.**
어느 쪽이든 근거를 알고 결정했다는 게 중요한 것 같아요.

한 달에 20달러면 커피 몇 잔 값인데, 여기까지 오는 데는 꽤 오래 걸렸습니다.
