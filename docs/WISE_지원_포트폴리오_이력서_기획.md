## 2. 포트폴리오(상세 사례집)에 넣을 내용

포트폴리오는 이력서보다 훨씬 깊게, **"어떤 문제를, 왜 그렇게, 어떻게 풀었고, 결과가 어땠는지"**를 보여주는 곳입니다. 아래 9개 사례 중 최소 5~6개를 골라 각각 "문제 → 시도 → 실패/전환 → 결과(숫자)" 구조의 미니 케이스 스터디로 작성하는 걸 추천합니다. Wise는 JD에서 "문제 해결", "운영팀 지원", "지속적 배포", "쿼리 최적화"를 명시적으로 언급했으므로, 이 순서로 우선순위를 두세요.

### 프로젝트 개요 섹션 (포트폴리오 최상단)
- 한 줄 소개: "30일 뒤 파멸할 운명의 조연 '시녀'가 '공주'가 되는 서사를 빌려온 자기계발 챌린지 서비스"
- 만든 이유/배경 (1~2문장): 팀 기획으로 시작된 실제 운영 서비스, 참가자 실제 예치금이 걸려 있어 신뢰성/보안이 실제 요구사항이었음
- 내 역할: 백엔드/프론트엔드/인프라/AI 연동을 단독으로 담당한 풀스택 개발자 (팀에는 기획자 등 비개발 직군 협업자 존재)
- 기간/규모: 2026.07.10 ~ 2026.08.21(6주), 68 커밋, 백엔드 자바 파일 122개, 프론트 TS/TSX 파일 38개
- 라이브 링크, GitHub 링크, (있다면) 데모 영상/스크린샷

### 사례 1 — AI 비용 최적화 (숫자로 증명하는 문제 해결력)
- 문제: Vision 인증 비용이 예상(월 2,500~4,000원)의 7배(28,300원)로 청구
- 원인 분석: OpenAI가 이미지를 모델별로 다르게 토큰화한다는 사실을 직접 계산해서 규명 (gpt-4o-mini는 이미지에 약 33배 가중치)
- 해결: Vision/피드백 모델 분리(gpt-4.1-mini / gpt-4o-mini), 업로드 이미지 리사이즈(1024px)
- 결과: 월 28,300원 → 5,100원 (82% 절감), 저장 용량도 720MB → 150MB
- 포트폴리오 팁: `docs/blog_사이드프로젝트기록1.md`에 이미 잘 정리된 글이 있으니 그대로 각색해서 넣으면 좋음. 비용 비교 표를 시각 자료로 넣기 좋은 소재.

### 사례 2 — 신뢰할 수 없는 입력 데이터 처리 (보안/설계 판단력)
- 문제: 인증 사진에 실제 예치금(10만원)이 걸려 있어 위변조 방지가 필요
- 1차 시도: EXIF 촬영일시 검증 → 팀원 질문("조작하면요?")으로 EXIF는 텍스트 필드라 쉽게 조작 가능함을 인지
- 전환: "검증"이 아니라 "입력 경로 통제"로 접근 전환. `getUserMedia`+Canvas로 카메라 전용 촬영 구현, 갤러리 접근 자체를 차단
- 트레이드오프를 숨기지 않고 서술: 스크린샷 업로드 불가라는 사용성 손실을 팀 논의로 수용, 운영으로 커버
- 결과: 조작 경로 원천 차단, 불필요해진 EXIF 검증 코드는 제거(느슨한 형태로만 잔존)
- 포트폴리오 팁: `docs/blog_사이드프로젝트기록2.md` 활용. "검증보다 입력 경로 통제가 확실하다"는 원칙을 한 문장으로 뽑으면 좋은 헤드라인이 됨.

### 사례 3 — 운영팀을 위한 셀프서비스 어드민 도구 (Wise JD와 가장 직접적으로 연결되는 사례)
- 문제: 12명 참가자의 주간 성공일수·환급 여부·MVP·점수 이의제기를 수기로 관리하기 어려움
- 설계: `users.role` 기반 RBAC, 주 단위 성공일수 자동 판정(전부 완료=1일/일부=0.5일), 6일 이상 시 환급 대상 자동 표시(최종 지급은 운영진 확인), 점수 보정을 삭제 기반 이력으로 남겨 추적 가능하게 설계, 한글 깨짐 없는 CSV 내보내기
- 결과: 운영진이 코드/DB 접근 없이 스스로 주간 운영 업무 처리 가능
- 포트폴리오 팁: Wise JD의 "셀프 서비스 솔루션을 구축하고 운영팀을 위한 효율적인 도구를 개발" 문장을 그대로 인용하며 "이 경험이 정확히 이런 종류의 일이었다"고 연결하면 설득력이 큼.

### 사례 4 — 채점 엔진 설계 (도메인 로직 정확성)
- 문제: DAILY/WEEKLY 두 종류의 미션 진행률을 계산해야 하고, 일간 결과를 그대로 7일 합산하면 WEEKLY 미션 점수가 최대 7배 중복 집계됨
- 해결: 주간 리포트는 일간 합산이 아니라 미션 타입별로 "정확히 1회"만 반영하는 별도 집계 로직(`getWeekTotalProgress`) 설계
- 검증: 실 MySQL 대상으로 "주 3회 미션을 2번 기록 → 1/3, 2/3로 누적되는지, 주간 합계가 정확히 2회분인지" curl로 직접 확인
- 결과: 점수 신뢰성 확보, 이후 QA 통과
- 포트폴리오 팁: 표/의사코드로 "잘못된 방식 vs 올바른 방식"을 나란히 보여주면 이해가 빠름.

### 사례 5 — 배포 인프라 트러블슈팅 (실전 장애 대응력)
- Railway 초기 로컬 업로드 배포가 로그 없이 계속 실패 → 원인을 파일 크기/설정파일/플랫폼 장애 순으로 하나씩 배제하며 GitHub 연동 배포로 전환
- Railway의 자동 빌더(Railpack)가 커밋된 `railway.json`(Dockerfile 지정)을 무시하는 문제를 GraphQL API로 직접 원인 규명, `dockerfilePath`를 명시적으로 재설정해 해결
- 빌드 성공 후에도 502 발생 → 로그에서 `Schema validation: missing table` 확인, 알고 보니 스키마 스크립트가 다른 DB(`princess_project`)에 생성돼 있었고 실제 앱은 Railway가 강제하는 `railway` DB를 사용 중이었음을 파악해 수정
- 결과: 배포 후 로그인→기록→주간리포트까지 실 프로덕션 URL로 E2E 검증 완료
- 포트폴리오 팁: 이 사례는 "인프라 문제를 포기하지 않고 단계적으로 원인을 좁혀가는 디버깅 태도"를 보여주는 좋은 소재. 타임라인 형태(1→11단계)로 정리된 원본이 `backend/PROGRESS.md`에 있음.

### 사례 6 — 성능/스키마 개선 (기술 부채 관리)
- N+1 쿼리 문제: 주간 참가자 목록 조회 시 참가자 1인당 9회 쿼리 발생 → 주 단위 배치 조회로 개선
- 스키마 관리 방식 전환: Hibernate `ddl-auto=update`(자동 변경, 추적 어려움) → 수기 `schema.sql` + `ddl-auto=validate`(엔티티와 실제 스키마 불일치 시 부팅 실패로 조기 발견)로 전환
- MySQL 특이 이슈 문서화: CHECK 제약이 걸린 컬럼에 CASCADE/SET NULL FK가 같이 있으면 MySQL 8.0.16+/9.x에서 에러(3823) 발생 → FK를 RESTRICT로 바꾸는 패턴을 문서화해 재발 방지
- 포트폴리오 팁: "발생 가능성이 큰 기술 부채를 사전에 문서화해 재사용 가능한 지식으로 남겼다"는 각도로 서술하면 JD의 "기술 부채를 사전에 파악하고 해결" 항목과 직결됨.

### 사례 7 — 스토리지 추상화 (벤더 중립적 설계)
- 배경: 실제로는 Railway Buckets(S3 프로토콜만 호환)를 쓰면서 코드/설정에는 `S3FileStorageClient`, `aws.s3.*`, `AWS_S3_*` 등 AWS 전용 네이밍이 남아있어 오해 소지
- 조치: `BucketFileStorageClient`, `storage.bucket.*`, `BUCKET_*`로 전면 리네이밍, AWS SDK의 암묵적 자격증명 체인 대신 명시적 프로퍼티로 자격증명 주입, path-style vs virtual-host style URL 차이를 감지해 옵션화
- 결과: 벤더 종속적 가정 없이 유지보수 가능한 코드로 정리
- (선택 사례 — 지면이 부족하면 사례 6에 통합해도 됨)

### 사례 8 — 인증/인가 설계
- JWT + BCrypt 비밀번호 해싱, 최초 로그인 시 자동 가입, 이후 로그인은 자격 불일치 시 401 처리
- 프로필 이미지 등 부가 리소스는 발급받은 토큰으로 후속 요청 처리(로그인 응답 자체는 JSON 유지해 기존 테스트 영향 최소화)
- 관리자 권한은 `users.role` 컬럼 기반 RBAC, `#id == principal` 형태의 SpEL 기반 리소스 소유권 검증(API 명세서에 권한 조건 명시)
