# 사이드프로젝트 기록 2. 사진 조작을 막으려다 검증 코드를 지운 이야기

지난 글에 이어서 사이드프로젝트 이야기입니다. 30일 챌린지 서비스를 만들고 있고, 저는 개발자로 참여하고 있어요.

이번엔 돈 이야기가 아니라 사람 이야기입니다. 정확히는 **사람을 못 믿는 이야기**요..

## 왜 사진을 검증해야 했나

이 챌린지에는 예치금이 있습니다. 참가비 20,000원과 별개로 100,000원을 걸고, 한 주에 6일 이상 인증에 성공하면 25,000원씩 돌려받는 구조에요. 4주 다 성공하면 전액 환급입니다.

즉 **인증 사진 한 장에 돈이 걸려 있습니다.**

그러면 당연히 이런 생각을 하게 됩니다. 어제 찍은 운동 사진 오늘 또 올리면 어떡하지? 지난주 독서 사진 재탕하면? 인터넷에서 아무 사진이나 주워오면?

물론 저희 참가자분들이 그럴 분들은 아닙니다.. 아니지만, 시스템은 그걸 전제로 만들면 안되잖아요. 무엇보다 성실하게 참여한 사람이 손해보면 안되니까요.

## 1차 시도 - EXIF를 읽자

사진 파일에는 EXIF라는게 들어있습니다. 카메라가 사진을 찍을 때 같이 기록하는 메타데이터인데요. 촬영 일시, 카메라 기종, 조리개값, 심지어 GPS 좌표까지 들어있습니다.

그래서 처음엔 이렇게 했어요. 업로드된 사진의 EXIF에서 촬영 일시를 꺼내서, 그게 오늘 날짜가 맞는지 확인하는 겁니다.

```java
Metadata metadata = ImageMetadataReader.readMetadata(inputStream);
// 촬영 일시를 꺼내서 오늘인지 확인
```

깔끔하죠. 라이브러리도 잘 나와있고, 코드도 몇 줄이면 끝납니다. 저는 이걸로 해결됐다고 생각했습니다.

## 그런데 EXIF는.. 고칠 수 있습니다

기획하시는 분이 물어보셨어요. "이거 사진 시간 조작하면 어떡해요?"

아.

EXIF는 사진 파일에 붙어있는 **그냥 텍스트 필드**입니다. 사진 자체가 아니에요. 무슨 워터마크처럼 픽셀에 박혀있는게 아니라, 파일 앞쪽에 별도로 저장된 데이터입니다.

그래서 고칠 수 있습니다. 그것도 아주 쉽게요.

- 맥은 기본 앱으로도 됩니다
- 윈도우는 파일 속성에서 됩니다
- 앱스토어에 EXIF 편집 앱이 널려있습니다
- 심지어 카톡으로 사진 보내면 EXIF가 통째로 날아갑니다 (이건 조작이 아니라 그냥 사라지는 케이스인데, 이것도 문제죠)

정리하면 제가 만든 검증은 **"조작할 줄 모르는 사람만 막는" 검증**이었습니다. 그리고 돈이 걸려있으면 사람은 검색을 합니다..

## 선택지가 두 개 있었어요

그래서 방향을 아예 틀기로 했습니다. 사진을 **검사**하는게 아니라, 사진이 **들어오는 길**을 막기로요.

방법이 두 가지 있었습니다.

**1. HTML의 capture 속성 쓰기**

```html
<input type="file" accept="image/*" capture="environment">
```

한 줄이면 됩니다. 모바일에서 이 input을 누르면 갤러리 대신 카메라가 바로 켜져요.

간단하고 좋은데, 문제가 하나 있습니다. **이건 강제가 아니라 힌트입니다.** 브라우저한테 "카메라 띄워주면 좋겠어"라고 요청하는 것이지, 갤러리 접근을 막는게 아니에요. 기종이나 브라우저에 따라 그냥 무시되고 파일 선택창이 뜨기도 합니다.

**2. getUserMedia로 직접 카메라 띄우기**

파일 선택 UI를 아예 없애고, 웹페이지 안에 카메라 화면을 직접 띄우는 방식입니다.

```javascript
const stream = await navigator.mediaDevices.getUserMedia({ video: ... });
// <video>에 스트림을 연결해서 미리보기
// 셔터를 누르면 그 순간 프레임을 <canvas>에 그림
ctx.drawImage(video, 0, 0, canvas.width, canvas.height);
canvas.toBlob(...)  // 이걸 업로드
```

코드는 더 깁니다. 카메라 권한 요청도 처리해야 하고, 권한 거부했을 때 안내도 띄워야 하고, 다 쓰고 나면 스트림도 꺼줘야 합니다. 안 그러면 카메라가 계속 켜져있어요 (이거 실수하면 진짜 무섭습니다).

대신 **파일을 고를 방법 자체가 없습니다.** 셔터를 누른 그 순간의 화면만 올라갑니다.

저희는 2번을 골랐습니다. 돈이 걸려있어서요.

## 여기서 예상 못한 일이 생겼습니다

카메라 전용으로 바꾸고 나서 기존 EXIF 검증 코드를 돌려봤는데, 전부 검증에 걸렸습니다.

왜냐하면.. **canvas로 그린 이미지에는 EXIF가 없기 때문입니다.**

당연한 얘기였어요. canvas는 픽셀만 다시 그리는 것이라, 원본 메타데이터가 따라오지 않습니다. 애초에 카메라 스트림에서 뽑은 한 프레임이라 "촬영 일시" 같은 개념 자체가 없고요.

그래서 어떻게 됐냐면요.

**조작을 막으려고 만든 EXIF 검증 코드가, 조작을 제대로 막고 나니까 쓸모가 없어졌습니다.**

이게 좀 웃겼습니다. 어차피 지금 이 순간 찍은 사진만 올라오는데, 그 사진이 오늘 찍은건지 확인할 이유가 없잖아요. 검증할 필요가 없어진거죠.

그래서 검증 코드를 지웠습니다. 정확히는 "EXIF가 있는데 날짜가 이상한 경우"만 남기고 느슨하게 풀었어요. 나중에 정책이 바뀌어서 업로드를 허용하게 되면 그때 다시 살아날 코드니까요.

## 대신 잃은 것도 있습니다

솔직하게 쓰자면, 이 선택으로 불편해진 부분이 있습니다.

**스크린샷을 못 올립니다.**

저희 공통과제 중에 독서랑 공부가 있는데요. 전자책으로 읽거나 인강으로 공부하는 분들은 화면을 캡처해서 올리는게 자연스럽습니다. 그런데 카메라 전용이라 그게 안돼요. 노트북 화면을 폰으로 찍어야 합니다.

QA 때 이 부분이 지적으로 올라왔고, 팀에서 논의했습니다. 결론은 **일단 카메라 전용 유지**였어요. 스크린샷을 허용하는 순간 갤러리 접근을 열어줘야 하고, 그러면 지금까지 막아둔게 전부 무의미해지니까요.

대신 운영으로 커버하기로 했습니다. 화면 찍는걸 안내하고, 애매한 케이스는 운영진이 직접 확인하는 식으로요. 완벽한 해결은 아니지만, 12명 규모에서는 이게 더 낫다고 판단했습니다.

## 여기서 남은 것

이번에 배운 건 이겁니다.

**데이터를 믿을 수 없을 때, 그 데이터를 더 열심히 검사하는건 답이 아닐 때가 많습니다.** 검사는 어차피 상대방이 정직하게 데이터를 만들었다는 전제 위에서 돌아가거든요. 그 전제가 깨지면 검사도 같이 깨집니다.

차라리 **데이터가 들어오는 경로를 좁히는게** 확실합니다. 조작할 수 없는 방법으로만 들어오게 만들면, 조작 여부를 검사할 필요 자체가 없어져요. 제 EXIF 검증 코드가 그래서 사라진 것이고요.

그리고 하나 더. 보안이나 검증 관련해서 뭘 만들 때는 **"이걸 뚫으려면 얼마나 귀찮은가"**를 같이 생각해야 하는 것 같습니다. EXIF 수정은 검색 3분이면 됩니다. 3분짜리 장벽 뒤에 10만원을 두면 안되죠.

지난 글에서도 그랬는데, 이번에도 결국 팀원 질문 하나에서 시작됐습니다. "이거 조작하면 어떡해요?" 혼자 했으면 저는 EXIF 파싱해놓고 뿌듯해했을 것 같아요. 협업이 좋은 이유가 이런 것 같습니다..
